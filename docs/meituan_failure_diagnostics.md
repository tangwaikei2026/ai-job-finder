# 美团持续请求失败：诊断修复与待确认决策

状态：BLOCKED_BY_DECISION。独立分支仅提供诊断，不部署、不启用收敛阈值。

## 已完成的安全修改

- 共用 HTTP 请求日志只输出固定异常类型/类别、白名单阶段、尝试次数和最终失败标志；最多遍历 8 层异常链识别 TLS，不输出异常正文、URL、请求参数或 Cookie。
- 所有平台现有请求次数、30 秒等既有 timeout 配置、退避、并发和调度保持原状。
- 美团记录平台进入/退出、每页列表进度、详情阶段进入、每 50 个详情完成后的进度及最终覆盖计数。元数据区分目标、已提交、已开始、成功、最终失败、未开始、尚未完成、正在处理。
- `detail_targets` 只代表已观察列表中的范围内岗位；列表未完成时，不代表全站目标数。`detail_unfinished` 包含未开始；`detail_failed` 仅统计已完成且失败的详情，不能把它与未完成混用。
- 最后成功时间表示列表页已映射或详情已成功应用的时刻；不以一次重试或 HTTP 200 代替有效采集进度。同时输出墙钟及 monotonic 耗时，列表/详情分段耗时进入 metadata。
- 保留原有 detail_error_types 桶、失败 ID、成功岗位内容、SourceHealth 和严格 completeness 语义；顶层错误摘要改为脱敏类型与阶段。

## 根因边界

每请求尝试最多 3 次，并不等于平台整体有界。当前美团一次提交全部详情，4 个线程持续处理，每个请求可分别耗尽尝试；`as_completed` 与线程池上下文退出均等待全部任务。串行平台采集因此拖住后续平台和 Daily 后续步骤。

HTTP timeout 是网络操作超时，不是请求端到端绝对截止时间。单用 `Future.cancel()` 不能停止已运行请求，`shutdown(wait=False)` 也不能证明解释器退出不等待线程。本批未改变这些行为，未实现或验证受控取消、绝对截止或平台早退；不得据诊断测试声明失败收敛已完成。

10/08、10/14 出现相似长等待机制；网络故障是否同源仍 UNKNOWN，历史空正文异常不能补猜类型。

完整成功批次是有幸存偏差的小样本，不足以承诺任意新阈值零误中断。

## 唯一建议方案（尚未批准、未启用）

建议美团平台总预算 **1800 秒 monotonic 计时**，从进入 collector 开始，覆盖列表、详情、重试与退避。在本机应区别于含休眠的墙钟时长。数值约为普通成功最大耗时的 4.8 倍、已知慢成功最大耗时的 1.5 倍。

风险：未来岗位规模增长、网络变慢仍可能截断最终可成功的采集；休眠时不会提供 30 分钟墙钟完成承诺。预算耗尽必须保留已成功结果，列表/详情不完整维持非 COMPLETE，未尝试/未完成不得当作已确认正文，也不得从缺失推断下架。

批准后仍需实现并验证：有限提交窗口、运行中请求的绝对截止与资源释放、退出线程等待边界、失败/未尝试 ID 覆盖及后续平台/分析证据链。不得直接假设现有 30 秒 HTTP timeout 能保证这些条件，不调整 SourceHealth 阈值。本批不提出无成功进度阈值，因历史缺少其正常分布。
