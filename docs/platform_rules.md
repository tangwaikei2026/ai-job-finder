# 采集平台接入规则

## 1. 接入前盘点

每个平台在实现前必须回答：

1. 平台属于公司 API、ATS、普通网页、浏览器依赖还是登录/高反爬。
2. 列表页和详情页分别能获得哪些字段。
3. 是否存在公开、稳定、无需动态签名的接口。
4. 请求是否需要 Cookie、动态 token、签名、验证码或登录。
5. robots、站点条款和数据使用边界是否允许当前用途。
6. 详情补全是否必要，以及其请求成本和限流风险。

## 2. Adapter 边界

- 一个新平台对应一个独立 adapter 文件。
- 平台特殊逻辑不得进入 `src/main.py`。
- 不得修改其他平台 adapter 的行为。
- 不得为了单个平台重构共享基础设施，除非已有至少两个明确消费者。
- Adapter 必须继承 `RawCollector` 并返回 `CollectionResult`。
- 所有岗位必须标准化为现有 `RawJobPosting`。

## 3. Raw 层职责

Raw 层允许：

- 请求和解析来源数据。
- 字段标准化。
- 城市范围过滤。
- 平台来源治理，例如排除猎头来源、无 ID 记录和重复记录。

Raw 层不允许：

- 复制或修改岗位池关键词规则。
- 为提高命中率向 description 注入搜索关键词。
- 修改 README 或 jobs 输出格式。
- 将行业、标签等不等价字段强行映射为 department。

## 4. 配置规则

以下内容必须配置化：

- URL 和 API marker。
- 关键词、城市、行业、岗位类型。
- page size、max pages、超时和重试。
- 浏览器 headless 开关。
- 详情开关和输出路径。
- 平台专用排除规则。

以下内容禁止配置化持久保存：

- Cookie。
- 会话 token。
- 一次性签名。
- 动态 `skId/fkId/ckId`。
- 账号和验证码信息。

新增平台默认应 `enabled: false`；任务明确要求默认启用时可以例外，并应在复盘中记录。

## 5. 列表采集规则

- 页码起点必须根据平台实际行为确认。
- 多关键词使用同一 `jobs_by_id` 去重。
- `max_pages` 必须明确是每关键词还是全局限制。
- 空页、重复页、短页、格式变化和请求失败必须有明确停止原因。
- 列表字段缺失不得导致整批失败。
- 缺少稳定 job_id 的记录应跳过，并增加 `missing_job_id`。

## 6. 浏览器规则

- 只有直接 HTTP 方案不可行时才能使用浏览器。
- 使用原因必须写入 adapter 注释。
- 浏览器依赖延迟导入。
- Browser、context 和 page 必须可靠关闭。
- 浏览器仅负责获取必须依赖会话的数据，解析逻辑应保持可单测。
- 禁止自动登录或绕过验证码，除非任务明确授权并完成合规评估。

## 7. 详情采集规则

- `fetch_details: false` 时不得发起详情请求。
- 开启详情前必须评估 403、429、验证码和安全跳转。
- 详情失败必须保留列表基础信息。
- 无法可靠拆分 JD 时，不应伪造 requirements。
- 对高反爬平台优先考虑列表-only 和人工复核。

## 8. 输出和失败规则

- 主输出继续使用现有 raw pipeline。
- 平台侧文件只能作为附加输出，结构必须与 RawJobPosting 一致。
- 使用原子写入。
- 完全失败不得覆盖上一次有效文件。
- 第一页失败应为 error；后续局部失败应为 partial。
- 错误信息必须可定位平台、关键词和页码。
- 单个平台异常不得向上击穿其他平台。

## 9. Liepin 当前约定

- 列表通过 Playwright 加载真实搜索页并监听 PC 搜索 API。
- 不直接重放私有列表 API。
- 遍历 `config.yaml` 中的 `keywords`。
- `max_pages` 按每关键词解释，当前为 1。
- 固定 `industry=H01$H01`、`job_kind=2`。
- 全部关键词结果按 `job_id` 去重。
- 当前 `fetch_details=false`，不自动请求详情。
- 人工复核文件为 `data/liepin/raw_job.json`。
