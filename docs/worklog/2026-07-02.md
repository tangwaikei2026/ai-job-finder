## 2. 今日遇到的问题

### 私有列表 API 返回 HTTP 200，但业务请求失败

问题现象：

- 直接 POST 猎聘搜索 API 得到 HTTP 200，但返回业务错误码 `-1400`。

根因：

- 接口依赖浏览器会话、动态参数和安全环境；仅复制 URL、请求体和常规请求头不足以通过校验。

最终解决方式：

- 使用 Playwright 打开真实搜索页，监听页面自身发出的 API 响应。
- 浏览器逻辑仅存在于猎聘 adapter，并采用延迟导入。

下次如何避免：

- 接入平台前同时检查 HTTP 状态和业务状态。
- 先做最小直接请求验证，再决定是否引入浏览器，不根据“公开 URL”假定接口可直接调用。

### 初始方案范围过大

问题现象：

- 早期实现包含完整分页、详情 JSON-LD、限流退避和详情熔断，超出了最终“列表供人工复核”的需求。

根因：

- 在产出范围尚未冻结时直接进入完整实现。
- 将可能需要的能力一次性做入，而没有按用户确认的阶段停下。

最终解决方式：

- 删除详情相关类、解析器、配置和测试。
- 收敛为关键词遍历、每词一页、列表字段映射、本地去重和侧文件输出。

下次如何避免：

- 开工前冻结本阶段输入、输出、停止点和明确不做项。
- 每个阶段只提交可独立验收的最小增量，用户确认后再进入下一阶段。

### 猎聘分支混入 JD 提交和生成数据

问题现象：

- `codex/liepin` 建立在多个 JD 提交之上。
- 一次提交中还包含约 30 万行 raw 生成数据和调研文档。

根因：

- 新平台分支没有从干净主分支创建。
- 提交前没有审查 `git diff --name-status master` 和提交体积。

最终解决方式：

- 工作树相对 `master` 已只保留猎聘所需的 5 个文件差异。
- 移除当前功能范围外的 JD 文件和生成数据。
- Git 历史重整仍待具备 `.git` 写权限时完成。

下次如何避免：

- 新平台必须从目标基线创建专用分支。
- 提交前检查分支 ancestry、文件清单、diff 统计和大文件。
- raw 产物默认不进入功能提交。

### 受限环境中的 Chromium smoke 无法启动

问题现象：

- Playwright 已安装，但 Chromium 在当前受限环境启动时因 macOS Mach 端口权限失败。

根因：

- 沙箱禁止 Chromium 注册所需的系统端口，不是 adapter 语法或 Playwright 安装问题。

最终解决方式：

- Adapter 捕获浏览器初始化异常并返回 error manifest。
- 修正输出策略：完全失败时不覆盖已有 `raw_job.json`。
- 单元测试通过 mock 浏览器边界完成确定性验证。
- 随后在具备浏览器权限的环境完成真实运行并输出 73 条岗位，证明实现路径可用；两个关键词仍存在响应超时。

下次如何避免：

- 开始浏览器平台开发前先运行最小 browser launch preflight。
- 将“单元测试可通过”和“目标运行环境可启动浏览器”作为两个独立验收项。

### 完全失败会覆盖人工复核文件

问题现象：

- 第一次真实 smoke 因浏览器启动失败返回空列表，但仍写出了空 `raw_job.json`。

根因：

- 文件输出发生在 manifest 判定之前，没有区分“成功采集到空结果”和“根本未成功解析页面”。

最终解决方式：

- 仅当 `pages_fetched > 0` 时更新侧文件。
- 平台结构变化或浏览器初始化失败时保留上一次文件。

下次如何避免：

- 所有落盘逻辑必须区分成功空集、部分结果和完全失败。
- 写文件前检查完整性信号，使用原子替换，不先截断旧文件。

### Python 编译检查受到缓存目录权限影响

问题现象：

- `compileall` 尝试向用户缓存目录写入 `.pyc`，被环境权限拒绝。

根因：

- Python 缓存目录位于工作区可写范围之外。

最终解决方式：

- 设置 `PYTHONPYCACHEPREFIX=/tmp/ai-job-finder-pycache` 后完成编译检查。

下次如何避免：

- 在受限执行环境统一把 Python、pytest 和工具缓存指向 `/tmp` 或工作区缓存目录。

## 3. 可沉淀为工作手册的规则

### 开发流程规则

1. 开工前检查当前分支、工作树、基线和相对主分支 diff。
2. 先冻结本阶段范围：输入、输出、明确不做项和停止点。
3. 一个阶段只实现一个可验收增量，不提前实现下一阶段。
4. 用户改变方案时先删除失效设计，再补新逻辑，避免兼容两套路径。
5. 提交前检查文件清单、diff 规模、大文件和生成产物。

### 配置设计规则

1. 关键词、分页、超时、重试、输出路径等简单参数必须进入配置。
2. 不把动态 token、会话 ID 或安全参数写入配置。
3. 布尔开关应表达真实行为；`fetch_details: false` 时业务代码不能暗中请求详情。
4. 限制类配置必须说明语义，例如 `max_pages` 是每关键词限制，不是全局限制。
5. 新平台默认关闭；只有任务明确要求时才默认启用。

### 爬虫/采集平台接入规则

1. 先判断平台类型：公开 API、ATS、普通网页、浏览器依赖或登录/高反爬。
2. 同时验证 HTTP 状态、业务码、响应结构和最终跳转地址。
3. 只有直接 HTTP 不可行时才使用浏览器，并记录原因。
4. 浏览器只处理必须依赖浏览器的边界；解析、映射和去重保持为可单测的纯逻辑。
5. 多关键词采集必须使用平台 job_id 做全局去重。
6. raw 层不复制岗位池规则，只做城市范围和平台数据源治理。
7. 平台特有逻辑只进入独立 adapter 或 platform fixes。

### 错误处理规则

1. 单个平台失败不得导致整个 pipeline 崩溃。
2. 字段缺失使用安全空值或明确 fallback，不因单条脏数据失败。
3. 响应格式变化必须显式报错，不能静默返回空列表。
4. 部分成功保留已采集数据，并通过 manifest 暴露失败位置。
5. 完全失败不得覆盖上次有效产物。
6. 错误摘要进入 manifest，完整堆栈进入日志，避免产物被巨量日志污染。

### 测试补充规则

1. 平台 adapter 最少覆盖正常解析、重复数据和响应格式变化。
2. 浏览器和网络边界使用 mock，单测不依赖实时网站。
3. 输出文件需验证字段集合和序列化结构。
4. 失败测试需同时验证不崩溃、不误报成功、不覆盖旧数据。
5. 平台专项测试通过后必须运行全量测试。
6. 实时 smoke 独立执行，失败时区分代码问题、网站问题和环境问题。

### Review 检查规则

1. 是否只修改当前平台及必要注册、配置和测试文件。
2. 是否修改了岗位池规则、已有 adapter、main、模型或输出格式。
3. 配置项是否实际生效，是否存在未使用配置。
4. 是否存在详情请求、隐藏并发或超范围网络行为。
5. manifest 的 success、partial、error 和 complete 是否与真实状态一致。
6. 空结果是否可能覆盖有效数据。
7. 分支是否包含其他功能提交、生成数据或超大文件。
